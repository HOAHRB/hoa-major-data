# 我们如何组织课程与资料

学生在培养方案中看到的是一门门具体的课，而资料站还要回答三个问题：哪些课适合共用一份文档？哪些独立文档值得一起参考？学习这些内容时，有没有明确的先后顺序？

我们用**实体课程、宏课程、课程群和课程系列**分别表达这些关系。

| 概念 | 回答的问题 | 例子 |
| --- | --- | --- |
| 实体课程 | 我在这个专业、这个年级的培养方案中，具体修哪门课？ | 某专业 2025 级方案中的“计算思维与人工智能” |
| 宏课程 | 哪些实体课程的资料放在同一个文档入口维护？ | 计算思维与信息基础、计算思维与人工智能等共用“计算思维”文档 |
| 课程群 | 哪些宏课程的内容或资料值得相互参照？ | 为内容密切相关、但分别维护资料的课程建立关联 |
| 课程系列 | 哪些宏课程适合依次学习？ | 微积分第一册 → 微积分第二册 |

计算思维的例子描述已有的资料归并；课程群和系列的例子用于解释概念，不表示相关关系已经录入。

## 1. 实体课程：培养方案里的具体一门课

**实体课程是某个专业、某个年级培养方案中的具体课程记录。**

原始课号、名称、学分、学时、课程性质、考核方式和成绩构成都属于这份记录。同一个课号出现在两个专业中，不代表可以把其中一个专业的课程要求套到另一个专业上。

课程在多个学期开设时，可以分别展示开设记录。当年的教师和可选项目属于具体开课安排，不自动改变资料归属。

这也是我们遵循上游架构的基础：**先有培养方案中的课程记录，再从这些记录组织跨专业浏览。** 跨专业索引不能替代各培养方案自己的课程信息。

## 2. 宏课程：共同维护资料的单位

**宏课程是实体课程通过文档映射归并到的共同对象，以映射目标作为标识和文档载体。**

例如，不同培养方案中的“计算思维与信息基础”“计算思维与人工智能”“计算思维与人工智能 A”和旧版“大学计算机-计算思维导论”，各自保留课程记录，但目前共同使用一份计算思维文档。这个共同对象就是“计算思维”宏课程。

学生从自己的专业课程进入，看到的仍是本方案的课程名称、原始课号、学分和考核要求；需要阅读正文或下载资料时，使用共同的计算思维文档入口。文档内部可以说明不同版本的适用内容。

### 什么时候共用，什么时候分开？

判断依据是实际资料需求，包括课程内容、难度、考核方式，以及是否需要独立维护资料。

- 不同课号的资料适合一起维护，可以映射到同一个宏课程。
- 即使内容相近，若难度或考核差异使学生需要独立的习题、复习和考试资料，也可以保留为不同宏课程。
- 一个宏课程内部可以分章节说明不同学期或版本的适用范围。

宏课程的边界不只由课程名称或学术分类决定。共用一个宏课程，不表示实体课程完全等价、可以互相替代，也不统一它们的教务信息。

### 文档映射直接落实宏课程归属

```text
计算思维与信息基础       ─┐
计算思维与人工智能       ─┤
计算思维与人工智能 A     ─┼─ 文档映射 → 计算思维宏课程 → 共同的文档与资料
大学计算机-计算思维导论  ─┘
```

图中的每个课程名称代表相应培养方案中的课程记录，不是仅按名称建立的全局课程实体。

不另外维护一份“实体课程属于哪个宏课程”的名单。资料归并发生变化时，修改相应映射；各实体课程的原始身份保持不变。

## 3. 课程群：独立资料之间的内容关联

**课程群把内容、方法或资料密切相关的多个宏课程联系起来，方便相互参照。群内没有先后顺序。**

例如，人工智能专业的“神经网络”和土木专业的“土木机器学习”，如果分别需要独立资料，可以保留为不同宏课程。维护者确认它们有值得相互参考的具体内容后，可以加入同一课程群，无需合并文档。

课程群的成员是宏课程，不是逐条培养方案课程记录。同一宏课程可以属于多个课程群。“同领域课程”不另设一套关系。

仅仅同属一个宽泛领域，不足以自动成群。例如，不能只因为名称涉及体育，就把体育史、体育教学、运动训练自动归入同一课程群。判断依据是实际内容与资料之间的联系。

## 4. 课程系列：宏课程之间的有序单链

**课程系列给多个宏课程安排明确的学习顺序，只允许单链，不设置分支或并行。**

例如，第一册和第二册分别维护资料时，可以组织为：

```text
微积分第一册 → 微积分第二册
```

同一宏课程可以出现在不同系列中。系列用于本站的学习与资料导航，独立于培养方案中的分轨道课程，也不自动代表学校规定的先修要求。

### 体育（1）至体育（6）已经合并，怎么办？

它们虽然有学期顺序，但既然共同维护为一个体育宏课程，就不再将六门实体课程分别作为宏课程系列的节点。内部顺序通过文档章节和培养方案中的开设学期表达。

**有先后顺序，不一定需要建立系列。** 系列解决多个独立文档入口之间的顺序导航，不要求为了展示顺序而拆分已有资料。

## 维护时如何选择

| 实际需求 | 采用的方式 |
| --- | --- |
| 保留某专业、某年级的课程要求 | 维护方案中的实体课程记录 |
| 多门课适合共同维护一份文档 | 映射到同一个宏课程 |
| 课程相关，但需要独立资料 | 保留不同宏课程，按需加入课程群 |
| 多个宏课程有明确的学习先后 | 建立单链课程系列 |
| 顺序发生在一个宏课程内部 | 在文档及实体课程的开设信息中说明 |

课程群和课程系列可以使用同一批宏课程，但表达的关系不同，不能从彼此或文档映射自动推导。它们在独立的 `course_relations.toml` 中维护，不向上游映射表附加额外字段，也不录入未经确认的关系。

## 名称、成员和页面索引如何维护

宏课程、课程群和课程系列都有用于引用的 **ID**，以及供人阅读的**展示名称**。调整展示名称不会改变成员关系。宏课程的展示名称也不会替换专业方案中的实体课程名称。

宏课程名称在对应资料仓库的文档标题中维护，复用上游现有的标题提取规则。major-data 不重复登记名称，也不要求课程仓库新增字段或改写旧标题。

`course_relations.toml` 是新增的可选文件，仅包含群和系列两张表：

| 表 | 条目的键 | 维护的内容 |
| --- | --- | --- |
| `groups` | 课程群自身的 ID | `name`：展示名称；`members`：宏课程 ID 列表 |
| `series` | 课程系列自身的 ID | `name`：展示名称；`members`：按学习顺序排列的宏课程 ID 列表 |

**由群找课、由系列找课：成员列表只在群或系列一侧维护。** 不在课程仓库中重复填写所属群和系列。同一宏课程可以出现在多个群和多个系列中，支持多对多关联。

课程页面需要“由课找群”时，由构建程序反向生成索引：当前宏课程属于哪些群、哪些系列，以及在各系列中的前后节点。这个反向索引是派生结果，不由维护者填写。

例如，下面是一份格式示意，不是已经确认或录入的课程关系：

```toml
[groups.MachineLearning]
name = "机器学习课程群"
members = ["NeuralNetworks", "CivilMachineLearning"]

[series.MachineLearningApplications]
name = "机器学习应用系列"
members = ["NeuralNetworks", "CivilMachineLearning"]
```

群的成员排列不表达学习顺序；系列的成员排列就是唯一的单链顺序。每个群或系列至少包含两个不同宏课程，内部不能重复成员；系列因此不形成回环。不同群、不同系列之间允许重复使用同一宏课程。成员直接引用资料仓库 ID，不需要在 major-data 中另行注册宏课程。成员可以是显式映射目标，也可以是沿用原课号的一对一资料入口。

这些要求仅约束新增的关系文件，不对已有的上游映射条目追加格式限制。历史资料入口仍可按原规则使用，不要求补充新的名称字段。新建群和系列的 ID 使用大驼峰，宏课程的历史 ID 按下文迁移规则处理。

首批已录入微积分系列课程、微积分E系列课程，以及微积分（上）、微积分（下）、代数与几何三个课程群，完整成员见 `course_relations.toml`。后端读取并校验此文件，生成 `lib/data/course_relations.json`；文件缺失或群、系列为空时生成空关系，不改变已有映射及课程页面。

前端构建时生成按宏课程拆分的关系索引，以及按专业方案拆分的本方案课程入口。课程页在正文之后、课程开设情况之前显示所属课程群和课程系列，保留当前宏课程并以定位图标标识；没有所属关系则不显示。点击成员后统一打开入口面板，展示本方案中对应的实体课程，并提供 GitHub 资料仓库入口；手机端使用抽屉。此功能不建立或下发跨专业开设记录，初始面板随页面渲染，不依赖异步请求。

### 课程文档中的名称放在哪里？

沿用课程仓库已有的 README 标题。例如 `ComputationalThinking` 仓库可以使用：

```markdown
# 计算思维系列课程
```

旧仓库已有的 `# 编号 - 课程名` 和现有 `title:` 写法继续按上游规则读取，不要求为了课程群功能统一重写。课程群、系列的展示名称在关系文件的 `name` 中维护；宏课程的展示名称从课程仓库读取，两边各有唯一来源。

构建过程复用后端现有的 `title_from_mdx` 标题提取规则，不另写一套含义不同的解析逻辑。培养方案课程页的标题仍取本方案课程名称；仓库文档标题用于宏课程的群、系列导航，不能覆盖实体课程名称。

仓库不存在或无法取得可用标题时，导航可暂时使用仓库 ID 并报告缺失资料，不根据某个专业的课程名称猜测宏课程名称。关系文件缺失或关系为空时，原有课程页面继续正常生成。

## 数据与命名约定

以下规则用于把上述概念落实到数据，不改变上游映射文件格式。`lookup_table.toml` 的键仍是原始课号，值仍是资料仓库 ID。

沿用上游解析规则：

1. 按原始课号找到映射表，优先匹配当前 `plan_ID`。
2. 未匹配时使用 `DEFAULT`，兼容已有的 `default`。
3. 没有适用映射时，以原始课号作为资料仓库 ID。

当前数据维护策略是否使用方案覆盖项，由 README 中的数据范围约定决定；不能因此删除解析器对上游方案覆盖规则的支持。

### 标识命名

显式归并多个课号的宏课程采用语义化大驼峰（PascalCase）标识，不借用其中某个实体课程的课号。例如：

- `PhysicalEducation`
- `ComputationalThinking`
- `Calculus1`、`Calculus2`
- `MilitaryTraining`

数字直接接在名称后，不使用 `Calculus-1` 形式。不同资料层次或系列应有可区分的名称，不能因改名抹去已有的分组边界。

未显式归并的一对一资料入口仍允许沿用上游的课号回退。仅重命名宏课程时，不改变映射表的原始课号键，也不重写培养方案中的课号。

显式归并目标使用上述大驼峰命名，具体映射目标见 `lookup_table.toml`，展示名称由各目标仓库的文档标题维护。当前仅 `MilitaryTraining` 资料仓库已存在，其他宏课程的目标仓库尚待建立。映射目标命名不表示正文或下载资料已经可用；实体课程的原始课号和页面身份保持不变。
